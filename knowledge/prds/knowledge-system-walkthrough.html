Knowledge-system walkthrough

One session, start to finish

Draft · Full flow for review · Planned system behavior

Visual companion to knowledge/prds/knowledge-system.md. Work item: Make the second brain reliable in real project sessions.

Required: must happen. Conditional: happens when its stated condition applies. Owner choice: the owner decides.

System guidance and completion checks are required outcomes. The supported triggers, hooks, or other mechanisms will be selected and tested during solution design.

Checkpoints confirm applicable guidance and required steps. The agent chooses how to reason and investigate. An acknowledgement does not prove understanding; answers and saved results must also meet the relevant rules.

Component ownership: the knowledge system operates within the toolkit OS. Steps marked “Separate process” or “Separate plugin” use that component's own rules and records, then return the result to this flow. They do not become new knowledge-system responsibilities.

The connected flow

Read the required startup files → confirm the manual was read
↓
Understand the request and current work → consider relevant memory → use a work item if needed
↓
Use relevant knowledge to do the work → keep changed work records current
↓
Decide what to save from the work → get any needed approval → save and check
↓
Continue working or prepare a handoff → resume the work
Fix knowledge problems when needed → check the result → return to the interrupted step.
Unanswered or unfinished saves → preserve their state → resume only the authorized path.

4. Decide what to save from the work

Review what was learned, decided, or changed during the work. Decide whether any knowledge record needs an update. If nothing needs saving, continue working. This review can also happen during earlier parts.

Required review moments · System guidance and checks
Prompt and check the review at the required moments
Review work since the previous review when a work item finishes or closes, before opening a pull request, before a handoff or context clear, at the end of a turn with real work, and whenever the owner requests a save.
The agent also judges when a useful fix, decision, upcoming commit, or meaningful context change warrants a review during work. A required review can result in no write.

Preserve verbatim quotations, captured outside documentation, and other original source material. Keep required file structure, metadata, exact names, and explicitly requested wording intact. Explain necessary technical terms; brevity must not remove important meaning. Reference the style instead of copying its rules into each knowledge procedure.

File formats and YAML fields the agent must follow
Long-term memory: one coherent Markdown file per topic by default. Keep related context together; do not create one file per fact. Recommend splitting into coherent subtopic files in one topic folder when it would make the information easier to find, understand, or use. Apply the split after required approval and preserve the approved meaning. Memory files have no fixed character limit. Each file uses YAML frontmatter. Required fields: summary, group, type, status, source, context, confidence, created_at, updated_at, tags, approved_by, approval_date.
type: fact, decision, event, context, constraint. status: current, superseded, retired. confidence: observed, reported, inferred. tags: a free-form YAML list of strings.
Dates use YYYY-MM-DD. Preserve the creation date; an update date is not proof of verification. Optional fields, used only when applicable: confirmed_at, source_quote, effective_from, effective_to, project, work_item, supersedes, superseded_by, related_memories.
Body: after the YAML properties, start with a title heading that names the memory topic. Use paragraphs, lists, or topic-specific headings that fit the information. Include enough context for a future agent to understand and use the memory without the original conversation. No fixed “Current understanding” or “Reason for the decision” headings are required. Include reasons or history when they help explain the information.
Optional sections: use When to revisit for a known condition or time that makes another review useful, and Related records for useful links to other records. Omit either section when it does not apply; do not invent review dates, conditions, or links to fill the template.

What kind of change is needed?
Clear mechanical repair: update links after an unambiguous rename, or rebuild a generated index from its source files. No new meaning approval is needed. Check the affected files before changing them.
