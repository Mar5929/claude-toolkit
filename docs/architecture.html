claude-toolkit · system map

One repo. One init skill. Many reusable prompts.

Your instinct was right. Here's the shape, and the one refinement that keeps each reusable system able to evolve on its own.

01

The repo is the single source of truth

Everything reusable lives here once. Copper = the orchestrator. Teal = self-contained reusable prompts it points to.

claude-toolkit/ ├─ README.md ← purpose + roadmap ├─ .claude-plugin/ │ └─ marketplace.json ← makes it installable └─ plugins/ └─ project-init/ ← orchestrator (project-init + project-sync) └─ second-brain/ memory + knowledge + structural layers └─ sf-architect-solutioning/ Salesforce solution architect └─ git-workflows/ parallel-session-safe git sync

project-init, the orchestrator

A thin "conductor" skill. Its whole job: walk you through setup, gate by gate, and point to the reusable prompts when you want one. It holds almost no content itself.

Reusable prompts, each its own skill

Memory architecture, knowledge layer, hook guards, CLAUDE.md rules. Each is a standalone instruction set (a SKILL.md = a structured prompt + templates) that can be improved on its own.

Why split them?

So you can refine the memory system without touching the init flow, and reuse it standalone. That's the modularity you asked for.

↓ install once per machine: /plugin marketplace add mar5929/claude-toolkit
02

It rides onto every device

One source, three delivery paths.

Mac + Windows

Claude Code plugin

Add the marketplace once; /plugin marketplace update git-pulls new versions.

Any machine

Symlink fallback

Clone + symlink skills into ~/.claude/skills/; git pull to update.

Desktop + Web

Publish target

No git auto-sync; upload the skill folder. The repo stays the source; you export on change.

↓ you start a new project and run /project-init

Your mental model, confirmed, with one refinement

"Is it gonna be like a repo, then an initialization skill, then pointing to prompts? … the memory architecture is basically just gonna take that prompt from the toolkit repo and say, use this prompt to create this."

Yes, that's exactly it. Repo → init skill → reusable prompts it points at. When you ask to set up memory, init pulls that stored prompt and runs it in the new project.

The one refinement: make each reusable prompt its own skill rather than a loose file buried inside project-init. Same behavior you pictured, but now the memory architecture can be versioned, fixed, and reused entirely on its own, and project-init stays a thin conductor that just knows how to call it.
