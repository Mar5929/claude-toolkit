## Section 3. Where a better or simpler solution exists

**1. Deliver the routing table when routing happens, not at startup.**
The design puts requirement 18's table into a manual that the startup hook prints in full. That is 3,595 characters spent in every session, on every harness, to answer a question that comes up only at a save. Requirement 2 itself says detailed rules are opened when they are needed. Putting both tables in `knowledge-save/references/routing.md` costs nothing until the save skill runs, which is the only moment the agent routes anything, and it frees the whole manual budget. This is the same fix as B2 and it also removes B1's largest single item.

**2. Run the after-write reconciliation once per turn, not once per Bash call.**
The design registers a `PostToolUse` hook on every `Bash` call with no filter. The `Stop` hook already runs at the end of each turn, already computes changed files from Git, and already carries `additionalContext`. Moving the reconciliation there gives the same coverage of `sed`, heredoc and `python -c` writes, spends one process per turn instead of one per command, and drops a beta field dependency. See S2.

**3. Deny `Write` on the two shared files and require `Edit`.**
The parallel-session case is the owner's stated working pattern and the design leaves it as guidance. `Edit` compares `old_string` against the file's current content, so a stale edit fails and forces a re-read; `Write` replaces the whole file with no comparison. One matcher line in the write guard turns "reread before replacing" from a hope into a mechanism, and it costs nothing when the agent already uses `Edit`. See S3.

**4. Keep a very small `UserPromptSubmit` hook instead of dropping it.**
The design drops `memory-reminder.mjs` for a good reason, 1,292 characters on every message, and then has nothing at the per-request moment. The walkthrough marks that moment as "guidance and check" and requirement 29 sanctions the lightest form of it. About 120 characters, once per request, only when no knowledge read has happened yet, is a tenth of the cost and covers the step the design currently answers with "Nothing". See S1.

**5. Print two glossary columns always, instead of choosing between the whole file and a path.**
The design's two options are whole file under 2,000 characters or nothing but a path. The agent does not need the `Watch out` and `Source / date` columns at the first message; it needs to recognise a term and know where to look. Two columns of forty terms fit in under 1,000 characters, which makes the 2,000-character cliff disappear. See S9.

**6. Size the startup print from the budget, not per file.**
Capping each file separately and then hoping the sum fits is why B1 exists. One budget, filled in an order that puts the cheap high-value items first (glossary two columns, inbox state lines, index entry lines), then `SOUL.md` and `project.md`, then the manual, then as much of `current.md` as remains, produces a map that degrades where it hurts least. The design's own `entriesOnly()` idea, kept from the shipped hook, is the right pattern; it just needs applying to `current.md` too.

**7. Verify the `current.md` publication instead of asserting it.**
The after-write hook is already at the right place at the right time. Two Git commands turn requirement 3's "confirms that the update is available to the next project session" into a checked fact. See S10.

## Section 4. Verdict

**Pass with fixes.**

This is a strong design. It is written in plain language a junior reader can follow, it keeps the agent at the centre, it uses documented harness features rather than inventing machinery, it names its limits instead of hiding them, and its Codex section and its refused-options list are better than most designs of this size. The measured fact that the shipped startup hook prints 20,585 characters against a 10,000-character cap is the kind of evidence that should sit under every design decision, and here it does.

Three things most need to change before this is built.

1. **Make the startup budget add up, and stop trying to fit requirement 18's table into a printed manual.** B1 and B2 are the same failure seen from two sides: the design sets per-part caps that sum to about 15,770 characters against a 9,500 budget, and it budgets 1,900 characters for a table that is 3,595 characters with the part requirement 18 also requires. Left as written, the first thing the map drops in a mature project is the glossary, the indexes and the inbox lines, which are exactly what requirements 7, 19 and 28 need at startup. Fix by moving the routing table to `knowledge-save`'s references, printing `current.md` in summary form, and budgeting the whole print rather than each file.

2. **Close the two requirements the design does not deliver at all.** Requirement 9's interview clause appears nowhere in the design (B5), and requirement 17's recommended answer contradicts the requirement's own Check and depends on a skill-authoring process that does not exist in this toolkit (B4). Requirement 2's manual content list is short by two items (B3). All three are small edits, but each one is a Check that today's design cannot pass.

3. **Add the lightest checks the requirements already allow, and correct three enforcement labels.** Requirement 29 asks for a confirmation that knowledge was consulted; the design builds nothing there and answers the walkthrough's two checkpoint steps with "Nothing" (S1). Requirement 3 asks for a confirmation that shared context reached other sessions; the design asserts it without checking (S10). Requirement 13's parallel-write case has a one-line mechanism available and unused (S3). And section 7 says ENFORCED for three rows the harness does not enforce (S7), which is the one place a document this honest overstates itself.

Section 13 is fair on the nineteen items it raises, and each recommended answer is the better one except §13.7, where the recommendation contradicts the requirement it is answering. Four entries are missing, listed in S12.
