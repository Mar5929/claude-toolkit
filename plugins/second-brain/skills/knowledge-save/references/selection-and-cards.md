# Select information and request missing permission

Route each meaningful part to its owner using section 2 of
`knowledge/knowledge-manual.md` (`docs/knowledge-manual.md` in `external`
mode). A requirement,
research finding, design rationale, temporary to-do and lasting lesson can arise
in one message and belong in different places. Do not lose useful non-memory
information by applying the memory exclusions to everything.

For lasting memory, all three must hold: project relevance, significant future
usefulness, and owner participation or joint work. Only a significant project
failure independently found and fixed may skip owner participation. A completed
exercise qualifies as an event only under those same tests: say what was done,
what resulted and where its useful output lives. Routine commands, package
updates, tool activity, transcripts, raw errors, secrets, reconstructible system
explanations and live task status fail the test. A withdrawn false conclusion
that spread may be worth keeping so later agents avoid it. Research findings
belong in the item's supporting research; rejected-design rationale in its design.

Before proposing: consider relevant selection feedback; find existing topic
and pending entries; verify sources, contradictions and duplicates; determine
operation and affected scope. Resolve uncertainty that would alter the save.
Ask one focused question when only the owner can resolve it, before the card.
An unrelated unresolved question does not hold a supported save.

Use permission already covering this operation and meaning. Named PRD drafting
permission covers faithful in-scope answers, not agent-invented requirements.
After authorized work ships, agreed behavior may update affected PRDs without
a new card; delivery never finalizes requirements or approves defects. An explicit
hold still applies. Automatic memory permission must be currently enabled in
`knowledge/project.md` (`PROJECT.md` in `external` mode), with grant person/date/source/scope recorded once; it
covers memory lifecycle operations and never PRDs. The template describes fields.
The setting is off by default. Recheck current authority before execution.

When missing permission requires a card, finish the main answer first, then a
horizontal divider and one destination heading per nonempty group:
`Proposed memory saves`, `Proposed PRD saves`, or the other owner's name.
Number cards uniquely across the reply. Other components retain their own formats.

Render this as Markdown, not a code fence:

### 1. Customer import decisions

**Change:** Update the existing customer-import topic, replacing the earlier
name-only matching decision.

**Summary:** Match customers using the agreed customer identifier. Two different
customers can share a name, so a name alone must not combine their records.

**Your decision:** Save this understanding? Approve, request changes, or decline.

This example is fictional, not an authorized project decision. For removal or
status-only changes use **Affected content** instead of Summary, identifying or
quoting exactly what is affected and explaining the result. A consolidation card
names all originals and the replacement. Show sources, reasons and consequences
when they affect the decision; exact paths, tags and routine checks may be linked
as details. The owner need not review the full entry to approve a faithful account.

One yes approves the displayed operation, meaning and scope, not extra work.
Partial approval applies only to selected numbers. A corrected and approved
summary is the new scope. Preserve words exactly only when explicitly requested;
otherwise write a faithful account. Resolve a conflict between required verbatim
wording and writing rules before approval. Silence, edits without clear approval,
and a request to see full text keep the proposal awaiting approval.

After showing an unanswered card, retain its exact text/layout in the inbox
(a `pending` record in `external` mode).
Keep its reference through revisions and identify which revision was approved.
Never make up a card or individual approval for authorized upkeep. Meaningful
feedback updates the feedback file (the `feedback` record in `external` mode)
under existing maintenance authority; it does
not turn the candidate into approved knowledge. Continue independent work.
