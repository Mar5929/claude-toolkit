# Keep a Running List of Everything Still Open in This Session

Claude Code has a built-in task list. Use it. A session that covers more than
one unresolved thing keeps that list current without being asked, so the owner
can see every open topic at a glance instead of holding them in their head.

## When to start one

The moment a second topic goes unresolved in the same session. One topic, or a
question answered in the turn it was asked, needs no list; a list for a single
item is noise.

Start it as soon as the second one appears, not at the end. A list written at
wrap-up is a summary, and by then the details that made each item findable are
already buried.

## What goes on it

Every topic that is still open, including the ones easy to lose:

- **Something the owner parked.** It stays on the list, marked parked. Parked is
  not finished, and it is never removed without the owner saying so.
- **Something waiting on background work.** The item says what it is waiting on.
  Background work finishing is not the same as the topic being resolved.
- **Something blocked by another item.** Say which item is blocking it.
- **A question asked of the owner that they have not answered yet.**

## What each entry has to carry

Enough that a different person could pick it up cold: what has to be decided or
done, and the numbers, names, and file paths already established. An entry
reading "fix the index" is worthless a day later.

## Keeping it honest

- Mark an item finished only when it actually is. Not when the work is nearly
  done, not when a check is still failing, and not when the last step was
  skipped.
- When the owner corrects an item, the correction wins, in that turn.
- Say in one line when an item closes. Do not narrate every update.

## What the list is not

It does not survive the session ending or the context being cleared. So anything
that has to outlive this conversation belongs in the project's work tracker or
inside a handoff prompt, and the owner is told that plainly rather than finding
out when it is gone.

A session list is also not a substitute for the tracker. When a topic turns into
real work, it gets a ticket, and the project's spec rule decides what that ticket
has to say before anyone builds.

## Why

A long session drifts across unrelated topics, and the earlier ones fall out of
view exactly when they are still unresolved. Without a list the owner has to
notice the drift themselves and ask what happened to the other four things,
which is the work this rule exists to take off them.
